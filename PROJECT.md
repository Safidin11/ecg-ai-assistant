# ECG AI Assistant — проектная документация

## 0. Дисклеймер

**Это не сертифицированное медицинское изделие.** Проект носит учебный и
исследовательский характер. Результаты работы модели (вероятности диагнозов)
не должны использоваться для принятия клинических решений, постановки
диагноза или назначения лечения. Любое реальное клиническое применение
требует сертификации, клинической валидации и соответствия регуляторным
требованиям (в РФ — регистрация как медицинское изделие, в ЕС — CE marking /
MDR, в США — FDA clearance). Дисклеймер должен быть виден пользователю в
интерфейсе на каждом экране, где показываются результаты.

## 1. Архитектура пайплайна

Проект состоит из 4 блоков, слабо связанных друг с другом через файлы и БД —
это позволяет независимо развивать и заменять каждый блок.

```
[Изображение ЭКГ] --> (1) Дигитайзер --> [сигнал: 12 отведений x N отсчётов, мВ]
                                              |
                                              v
                                     (2) База данных
                                     (recordings, predictions)
                                              |
                                              v
                                   (3) Модель диагностики
                                   (сигнал -> вероятности диагнозов)
                                              |
                                              v
                                     (4) Веб-интерфейс
                                (загрузка, просмотр результата)
```

### 1.1. Дигитайзер (`digitizer/`)

Вход: изображение/скан бумажной ЭКГ-ленты (jpg/png/pdf).
Выход: цифровой сигнал — массив формы `[12, N]` в милливольтах + частота
дискретизации.

На первом этапе используется готовый сторонний репозиторий/алгоритм
(подключается позже), собственная разработка дигитайзера — предмет этапа 2.

Пока код не подключен, слой должен быть изолирован интерфейсом
(`services/digitizer_service.py` в бэкенде), чтобы конкретную реализацию
можно было заменить без изменения остального пайплайна.

### 1.2. База данных (`backend/app/db/`)

SQLite на старте (файл `.db`, путь конфигурируется через `.env`). Сигналы и
изображения **не хранятся в БД** — только на диске (файлы WFDB или `.npy`),
в БД хранится путь до файла и метаданные. Это упрощает миграцию на другой
storage (S3 и т.п.) в будущем без изменения схемы БД.

#### Таблица `recordings`

| поле            | тип        | описание                                             |
|-----------------|------------|-------------------------------------------------------|
| id              | int, PK    | идентификатор записи                                   |
| created_at      | datetime   | дата/время загрузки                                    |
| image_path      | str        | путь к исходному изображению ЭКГ                       |
| signal_path     | str        | путь к оцифрованному сигналу (WFDB или .npy)            |
| sampling_rate   | int        | частота дискретизации, Гц                              |
| duration        | float      | длительность записи, сек                               |
| quality_score   | float, опц.| оценка качества оцифровки (0..1), если дигитайзер её даёт |
| notes           | str, опц.  | произвольные заметки                                    |

#### Таблица `predictions`

| поле            | тип        | описание                                              |
|-----------------|------------|--------------------------------------------------------|
| id              | int, PK    | идентификатор предсказания                              |
| recording_id    | int, FK    | ссылка на `recordings.id`                                |
| model_version   | str        | версия/имя модели, сделавшей предсказание                |
| probabilities   | JSON       | словарь `{диагноз: вероятность}`                         |
| diagnosis       | str        | итоговый (наиболее вероятный) диагноз                    |
| created_at      | datetime   | дата/время предсказания                                  |

Одна запись `recordings` может иметь несколько `predictions` — например,
после переобучения модели старую запись можно прогнать через новую версию,
не теряя историю.

### 1.3. Модель диагностики (`diagnosis/`)

Вход: сигнал `[12, N]` в мВ. Выход: вероятности диагнозов (набор классов —
как в PTB-XL: NORM, MI, STTC, CD, HYP и т.д., в зависимости от используемой
разметки).

Этап 1 — используется предобученная на PTB-XL модель (сторонняя, инференс
"как есть"). Обучение собственной модели откладывается на этап 3.

Как и дигитайзер, доступ к модели изолирован через
`services/diagnosis_service.py`, чтобы предобученную модель можно было
заменить на собственную без изменений в остальном коде.

### 1.4. Веб-интерфейс (`frontend/`)

На старте — простая статическая страница: загрузка изображения ЭКГ,
отображение результата (вероятности диагнозов) и дисклеймера. Полноценный
фронтенд (SPA-фреймворк, визуализация сигнала и т.д.) — предмет дальнейших
итераций.

## 2. Поток данных (end-to-end)

1. Пользователь загружает изображение ЭКГ через веб-интерфейс → `POST /recordings`.
2. Бэкенд сохраняет изображение на диск, вызывает дигитайзер → получает сигнал.
3. Сигнал сохраняется на диск (WFDB/npy), в БД создаётся запись `recordings`.
4. Бэкенд вызывает модель диагностики на сигнале → получает вероятности.
5. Результат сохраняется в `predictions`, связывается с `recordings.id`.
6. Веб-интерфейс запрашивает результат → `GET /recordings/{id}/predictions` → показывает пользователю (с дисклеймером).

## 3. План по этапам

### Этап 1 — рабочий скелет end-to-end (текущий)

- Структура проекта, БД, API-заготовка — **готово этим коммитом**.
- Подключить готовый сторонний дигитайзер (как чёрный ящик) в `digitizer/`.
- Подключить предобученную на PTB-XL модель (как чёрный ящик) в `diagnosis/`.
- Реализовать API: загрузка изображения → сигнал → предсказание → отдача результата.
- Минимальный фронтенд для ручной проверки пайплайна.
- Цель: убедиться, что весь путь от изображения до диагноза работает end-to-end,
  пусть и с грубым качеством на каждом шаге.

### Этап 2 — улучшение дигитайзера

- Оценка качества оцифровки на реальных/синтетических изображениях.
- Замена/доработка алгоритма дигитайзера, обработка шумов, наклона, обрезки.
- Возможно — сбор собственного датасета пар "изображение → сигнал" для валидации.

### Этап 3 — собственная модель диагностики

- Обучение модели на PTB-XL (и, возможно, других открытых датасетах) с нуля
  или дообучение (fine-tuning) предобученной.
- Сравнение с baseline-моделью из этапа 1 по метрикам (AUC, F1 по классам и т.д.).
- Версионирование моделей через поле `model_version` в `predictions`.

## 4. Ограничения и допущения

- Проект не проходил и не планирует в ближайшее время проходить клиническую
  валидацию или сертификацию как медицинское изделие.
- Датасеты (`data/`) не хранятся в git — предполагается их отдельная загрузка
  каждым разработчиком согласно лицензии датасета (например, PTB-XL на
  PhysioNet).
- Веса моделей (`*.pth`, `*.pt`, `*.h5`) также не хранятся в git — они либо
  скачиваются отдельно, либо кладутся в объектное хранилище на более поздних
  этапах.
